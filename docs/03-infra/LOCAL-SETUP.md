# التشغيل المحلي — المشروع بلا استضافة

> قرار صاحب المشروع: **لا استضافة، كل شيء محلي.** هذه الوثيقة تصف البيئة
> الفعلية وكيف تقوم من الصفر، وما الذي تغيّر في بوابة المرحلة 03 نتيجة القرار.

## قاعدة البيانات — PostgreSQL محمول

Docker غير متاح على جهاز التطوير: لا صلاحيات مدير، و WSL2 غير مثبَّت.
البديل المعتمد نسخة محمولة في `.localdb/` تعمل بلا تثبيت وبلا صلاحيات.

```bash
# تشغيل الخادم — يلزم بعد كل إقلاع للجهاز
.localdb/pgsql/bin/pg_ctl.exe -D .localdb/data \
  -o "-p 5432 -c listen_addresses=localhost" -l .localdb/pg.log start

# إيقافه
.localdb/pgsql/bin/pg_ctl.exe -D .localdb/data stop
```

`.localdb/` متجاهَل في git — القاعدة تُعاد بناؤها من المهاجرات والبذور، ولا تُنقل.

## الأوامر اليومية

| الأمر | ماذا يفعل |
|-------|-----------|
| `npm run verify` | **يهدم البيئة ويعيد بناءها ويفحصها كاملة** — عشر خطوات |
| `npm run verify:quick` | الفحوص بلا هدم قاعدة البيانات — أثناء العمل |
| `npm test -w @basta/api` | الاختبارات وحدها |
| `npm run db:migrate -w @basta/api` | مهاجرة جديدة |
| `npm run db:seed -w @basta/api` | إعادة البذور |
| `npm run db:backup-keygen` | **مرة واحدة**: زوج مفاتيح النسخ — العام في `.localdb/`، والخاص في `~/.basta/` |
| `npm run db:backup` | نسخة احتياطية **مشفّرة** (`.dump.enc`) — تكفيها المفاتيح العامة |
| `npm run db:verify-restore` | **يفكّها ويستعيدها على قاعدة نظيفة ويتحقّق أن الحرّاس نجت** |
| `npm run db:backup-seal-legacy` | يشفّر النسخ القديمة المكشوفة (`.dump`) ويحذف أصلها بعد التحقق من كلٍّ |
| `npm run dev:api` · `npm run dev:web` | خادم التطوير |

## النسخ الاحتياطية مشفّرة

المشروع داخل مجلد يزامنه OneDrive، فكل ملف في `.localdb/backups` يصل سحابة طرف ثالث. لذلك
النسخة تُشفَّر وهي تُكتب (X25519 + AES-256-GCM، `scripts/lib/backup-crypt.mjs`) ولا يلمس نصّها القرص:

- **المفتاح العام** (`.localdb/backup-key.pub`) يكفي للنسخ — لا يفكّ شيئاً.
- **المفتاح الخاص** (`~/.basta/backup-key.pem`) للاستعادة وحدها، خارج المشروع وخارج OneDrive.
  **احفظ نسخة منه خارج الجهاز** (مدير كلمات المرور): ضياعه يعني ضياع كل نسخة.
- النسخ المشفّرة نفسها يصحّ أن تزامنها السحابة — تصير نسخة خارج الموقع لا يقرؤها أحد.
- المساران يتغيّران بـ `BACKUP_PUBLIC_KEY` و `BACKUP_PRIVATE_KEY`، والمجلد بـ `BACKUP_DIR`.

ملف معدَّل أو مبتور يُرفض ولا يُكتب منه شيء. `verify` وتمرين التراجع يعملان بمفتاح عابر في مجلد
مؤقت — لا يراكمان نسخاً (كان كل تشغيل لـ verify يترك نسخة مكشوفة) ولا يحتاجان مفتاحك الخاص.

## ملفات الرفع — المرحلة 05

صور المنتجات تُكتب في `apps/api/uploads/` (أو ما يحدّده `UPLOADS_DIR`) وتُخدم على `/uploads/` من الخادم نفسه، بلا حارس مصادقة لأنها محتوى عام كصفحة المنتج. المجلد متجاهَل في git.
كل صورة تُفكّ وتُعاد كتابتها WebP و AVIF ومصغّرة 400 بكسل، ولا يُحفظ الأصل — فتسقط بيانات EXIF (موقع التصوير في صور الهواتف).

## الاختبارات الحيّة

ملفات `*.integration.spec.ts` تحتاج القاعدة شغّالة، وتتخطّى نفسها بدونها فيبقى `npm test` عاملاً.
اختبار الكتالوج يُقلع تطبيق Nest كاملاً بـ `configureApp` نفسها التي يُقلع بها الخادم، ولذلك يُحوَّل الكود في الاختبار بـ **SWC لا esbuild**: esbuild لا يُصدر بيانات المزخرفات، فيصل حقن التبعيات `undefined`.
اختبار التزامن يصنع السباق فعلاً: اتصال يمسك صف المخزون حتى يُرى كل المتسابقين واقفين على قفل في `pg_stat_activity`. نسخته الأولى نجحت والقفل منزوع — كان الطلب الأول يكتمل قبل بدء الثاني.

**بيانات الاختبار الحيّ لا تُحذف**: حركات المخزون للإضافة فقط. تُؤرشف المنتجات، و `npm run verify` يبني القاعدة من الصفر.

## ما تغيّر في بوابة المرحلة 03

البنود التي تفترض مزوّد استضافة لم تُشطب — **تُرجمت**. الهدف من كل بند بقي،
وتغيّرت صيغة إثباته:

| الهدف الأصلي | صيغته المحلية | الإثبات |
|--------------|----------------|---------|
| نشر آلي بلا تدخل يدوي | إعادة بناء البيئة من الصفر بأمر واحد | `npm run verify` — عشر خطوات |
| تراجع مجرَّب عن نشرة فاشلة | استعادة مجرَّبة من نسخة احتياطية | `npm run db:verify-restore` |
| تنبيه Sentry لخطأ مصطنع | سجل أخطاء دائم بمعرّف طلب | `logs/errors.jsonl` + اختبار |

**لماذا هذه ترجمة لا تنازل.** الغاية من النشر الآلي ليست وجود خادم بعيد، بل
أن يكون قيام النظام **مملّاً ومكرَّراً** لا طقساً يدوياً يعرفه شخص واحد.
`npm run verify` يثبت ذلك بهدم القاعدة فعلياً وإعادة بنائها — وهو اختبار
أقسى من نشرة تعتمد على حالة متراكمة على خادم.

والغاية من التنبيه أن **لا يمرّ خطأ صامتاً**. السجل الدائم يحقّقها: كل خطأ
غير متوقّع سطر JSONL بمعرّف طلب يربط بلاغ المستخدم بالسبب، والأسرار محذوفة
قبل الكتابة.

## ما بقي غير منفَّذ — وسببه

**بيئة تجريبية منفصلة ونشر عن بُعد.** لا مزوّد. البنية جاهزة: `Dockerfile`
لكل تطبيق، وخطّ فحص كامل في `.github/workflows/ci.yml`. متى وُجد مزوّد صار
التوصيل **إضافة أسرار لا إعادة بناء**.

**Sentry.** الكود موصول ومعطّل ذاتياً بلا `SENTRY_DSN`. يكفي وضع المفتاح في
`.env` ليعمل، و`GET /api/v1/health/boom` يرمي خطأً مقصوداً لإثبات الوصول.
البديل مفتوح المصدر GlitchTip متوافق مع البروتوكول نفسه ويُوصَل بنفس المتغيّر.

**Redis و Meilisearch — حُسما بتجربة في 20 سبتمبر 2026** ([ADR-014](../01-foundation/ADR.md)):

**البحث: Meilisearch محمول.** ملف تنفيذي واحد في `.localdb/meili/` يعمل بلا تثبيت وبلا صلاحيات، كـ PostgreSQL تماماً:

```bash
# تشغيل — المنفذ 7701 كي لا يزاحم الخادم (4000) ولا الواجهة (3000)
.localdb/meili/meilisearch.exe --http-addr 127.0.0.1:7701 \
  --db-path .localdb/meili/data --master-key basta_local_dev_key_0001 --env development
```

توحيد الهمزات والتشكيل والتسامح الإملائي يعمل جاهزاً على العربية، والزمن 1–2 مللي ثانية على 10,000 منتج. `.localdb/` خارج git، فالملف يُنزَّل مرة على كل جهاز (`scripts/probes/README.md` فيه الأمر).

**الطوابير: pg-boss على قاعدة بسطة نفسها، بلا Redis.** لا خدمة إضافية ولا منفذ ولا تشغيل يدوي بعد إقلاع الجهاز — الطابور جداول في مخطّط منفصل، والمهمة تُدرَج داخل معاملة الكتابة نفسها فلا يضيع حدث بسقوط الخادم بين الاثنتين.

مهمة تحرير الحجوزات المنتهية (كل دقيقة) تبقى **بمؤقّت داخل الخادم** حتى المرحلة 08، ثم تنتقل إلى pg-boss. هي عديمة الأثر عند التكرار، فتشغيل نسختين في اللحظة نفسها لا يُنقص المحجوز مرتين.
