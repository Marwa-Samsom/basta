## 1 · الاتجاه التصميمي

المنصة ثلاثة أسطح لجمهور مختلف، ونظام واحد يخدمها:

| السطح | من يستعمله | كيف يُقرأ |
|-------|-------------|-----------|
| المتجر | مشترٍ لا يعرف المنصة | يُتصفَّح ويُقارَن — مساحة مريحة، صور كبيرة، قرار شراء |
| لوحة البائع | بائع يعمل يومياً | تُشغَّل — كثافة عالية، جداول، عمليات متكررة |
| لوحة الإدارة | موظف مدرَّب | تُراقَب — أعلى كثافة، بيانات مالية، حالات استثناء |

**القرار:** نظام رموز واحد بكثافتين (`comfortable` / `compact`)، لا ثلاثة أنظمة. تبديل الكثافة يغيّر المسافة وحجم النص وارتفاع الصف — ولا يغيّر لوناً ولا مكوّناً. هذا يمنع انفصال اللوحات عن المتجر بصرياً بعد ستة أشهر من التطوير.

### الألوان — لماذا هذه بالذات

**النيلي `#2A4480` للعلامة.** مأخوذ من نيلة الصبّاغين، لا من أزرق افتراضي. يحمل ثقة يحتاجها سوق يتعامل بالمال، ويصمد على الأرضيتين الفاتحة والداكنة بعد رفع درجته في الداكن.

**الرمان `#B23A5B` للمال وحده.** هذه أهم قاعدة لونية في النظام: الرمان **محجوز للسعر والخصم والمجموع والرصيد**، ولا يُستعمل زينةً ولا للأزرار ولا للروابط. النتيجة أن عين المشتري تتعلّم خلال دقيقتين أن هذا اللون يعني رقماً يخصّ جيبه — وهو مكسب لا يشتريه أي قدر من التنميق.

**المحايدات بميل نيلي بارد.** رماديّ خالص (`#808080`) يقرأ كغير مقصود. الميل الطفيف نحو لون العلامة يجعل الصفحة تبدو مضبوطة لا مجمَّعة.

**الدلالات منفصلة تماماً.** أخضر/كهرماني/أحمر/سماوي لا علاقة لها بلون العلامة. حالة الطلب لا يجوز أن تشتبه بهوية المنصة.

## 4 · الحالات الحرجة — تُصمَّم أولاً لا أخيراً

الحالة الفارغة والخاطئة أكثر ما يراه المستخدم في منصة جديدة بلا محتوى بعد. تصميمها في آخر أسبوع هو سبب شعور المنصات الناشئة بأنها غير مكتملة.

| الحالة | القاعدة |
|--------|---------|
| سلة فارغة | لا رسم كرتوني — اقتراح فئات حقيقية وزر عودة للتصفّح |
| بحث بلا نتائج | بدائل مقترحة وتصحيح إملائي مقترح، لا صفحة فارغة |
| فشل الدفع | **سبب محدد** لا «حدث خطأ»، وزر إعادة محاولة يحفظ السلة كاملة |
| نفاد المخزون أثناء الدفع | **تسمية المنتج الناقص بالاسم**، وعرض إتمام الباقي |
| انتهاء مهلة الحجز | إعادة محاولة تلقائية، ورسالة واضحة إن نفد |
| بائع معلَّق | صفحته تبقى بلا منتجات، ورسالة محايدة لا تشهّر به |
| منطقة غير مغطاة | منع هذا البائع وحده، مع إبقاء باقي السلة |
| رصيد سالب | يُعرض للبائع بصراحة مع سببه وسبيل تسويته |
| لوحة بلا بيانات | صفوف مثال معلَّمة صراحةً كأمثلة، لا هيكل فارغ |

**قواعد كتابة الأخطاء:** ما الذي حدث، ولماذا، وما الخطوة التالية. بلا اعتذار وبلا تعميم. «فشل الدفع: رفض البنك العملية. جرّب بطاقة أخرى أو الدفع عند الاستلام.» لا: «عذراً، حدث خطأ ما.»

## 5 · قواعد RTL

المنصة عربية أولاً وتعمل LTR أيضاً. **الخصائص المنطقية تتكفّل بالانعكاس** (`inline-start`/`inline-end` بدل `left`/`right`) — عدا ثلاث حالات لا تنعكس تلقائياً وتُعالَج صراحةً في `tokens.css`:

1. **الأيقونات الاتجاهية** — سهم الرجوع والتالي يُقلبان بـ `scaleX(-1)`. أيقونة غير اتجاهية (سلة، بحث) لا تُقلب.
2. **الأرقام واللاتينية داخل نص عربي** — رقم الهاتف و`SKU-2024` ورقم التتبّع تحتاج `unicode-bidi: isolate`، وإلا انقلب ترتيبها. **هذا أكثر عيب RTL شيوعاً وأقلّه ملاحظةً في المراجعة.**
3. **الشعارات والعلامات التجارية** — لا تنعكس أبداً.

**اتجاه الزمن.** المخططات الزمنية ومؤشر الخطوات يتقدّمان من اليمين لليسار في العربية. Grid في RTL يفعل ذلك تلقائياً — وهو سلوك صحيح لا خطأ يُصحَّح.

## 6 · الوصولية

| البند | المعيار |
|-------|---------|
| تباين النص | AA — 4.5:1 للنص العادي، 3:1 للكبير، **على السمتين** |
| تباين الواجهة | 3:1 لحدود الحقول والأيقونات الدالّة |
| هدف اللمس | 44×44 بكسل حدّاً أدنى على الجوال |
| التركيز | مرئي دائماً بلون واحد، و`outline: none` بلا بديل يوقفه فحص CI |
| اللون وحده | لا يحمل معنى أبداً — حالة الطلب لها شارة نصية بجانب لونها |
| الحركة | `prefers-reduced-motion` مُحترم في كل انتقال |
| النماذج | كل حقل له `<label>` مرتبط، والخطأ مرتبط بـ `aria-describedby` |

## 7 · التدفقات الثلاثة

### أ · رحلة الشراء
```
اكتشاف (رئيسية/بحث/فئة)
  → صفحة منتج → اختيار متغيّر → إضافة للسلة   [لا حجز مخزون بعد]
  → السلة (مجمّعة حسب البائع، شحن لكل بائع)
  → إتمام الشراء ← ⏱ هنا يبدأ الحجز 15 دقيقة، والعدّاد ظاهر
      → عنوان → مراجعة → دفع
      ├─ نجاح  → صفحة تأكيد تعرض الطلبات الفرعية منفصلة بحالة كل بائع
      ├─ فشل   → سبب محدد + إعادة محاولة، والسلة محفوظة كاملة
      └─ انتهاء المهلة → إعادة حجز تلقائية، أو رسالة إن نفد المخزون
  → تتبّع الطلب (حالة مستقلة لكل بائع)
  → استلام → [14 يوماً مهلة إرجاع] → إتاحة المراجعة
```
**قرار تصميمي:** صفحة التأكيد تعرض الطلبات الفرعية **منفصلة من اللحظة الأولى**. إخفاء الانقسام يجعل المشتري يتوقّع طرداً واحداً، ثم يشتكي عند وصول ثلاثة في أيام مختلفة.

### ب · رحلة تأهيل البائع
```
تسجيل → رفع وثائق → قيد المراجعة
  ├─ رفض  → سبب مكتوب + إمكانية إعادة الرفع
  └─ قبول → اختيار عملة التسوية  [مرة واحدة، لا تتغيّر بعد أول بيع]
        → ملف المتجر → مناطق وأسعار الشحن → أول منتج → نشر
```
**قرار تصميمي:** اختيار عملة التسوية يظهر مرة واحدة مع تحذير صريح بأنه غير قابل للتغيير بعد أول بيع (ADR-013). قرار غير رجعي يُدفن في الإعدادات = نزاع مؤجَّل.

### ج · رحلة إدارة الطلب لدى البائع
```
إشعار طلب جديد → قبول [مهلة 48 ساعة، عدّاد ظاهر]
  → تجهيز → بوليصة ورقم تتبّع → شحن → تسليم
  → [14 يوماً] → تحرير الرصيد → السحب عند تجاوز الحد الأدنى
```
**قرار تصميمي:** الأزرار المعروضة = الانتقالات المسموحة من آلة الحالات فقط. الزر غير المسموح **لا يظهر معطّلاً بل لا يظهر**، والخادم يرفضه أيضاً — الاثنان معاً (ORDER-STATES §1).
